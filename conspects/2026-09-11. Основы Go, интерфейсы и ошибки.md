# Конспект занятий 1–2: основы Go, интерфейсы и обработка ошибок

# Занятие 1. Введение в Go и основы языка

## 1.1 Зачем вообще появился Go

Go создали в Google в 2007 году Роберт Гризмер, Роб Пайк и Кен Томпсон (авторы Unix, языка B, Plan 9 и — что забавно — самой кодировки UTF-8). Открытый релиз — 2009, Go 1.0 — 2012.

Мотивация была инженерная, а не академическая:

- сборка больших C++-проектов занимала десятки минут;
- управление зависимостями — ручной труд;
- многоядерность стала нормой, а треды ОС + мьютексы + разделяемая память — слишком сложны;
- порог входа в C++ для новых инженеров оказался слишком высоким.

Отсюда цели языка: компиляция за секунды, статическая типизация с выводом типов, безопасность памяти, конкурентность как часть языка (а не библиотеки) и один самодостаточный бинарник.

**Философия.** В Go около 25 ключевых слов (в C++ — порядка 90). Язык сознательно *не даёт* фичи: нет наследования, исключений, перегрузки функций и операторов, тернарного оператора, нет цикла `while`. Это дизайн-решение: код на Go читается одинаково в любой команде. Форматирование фиксирует `gofmt` — и споры о стиле в Go-командах просто не существуют.

**Чем Go НЕ является** (полезно знать заранее):

- не объектно-ориентированный в классическом смысле: нет классов и наследования, есть структуры + методы + встраивание + интерфейсы;
- не функциональный, хотя функции — значения первого класса, и замыкания есть;
- не «системный язык без рантайма»: GC встроен, арифметики указателей нет.

## 1.2 Тулчейн и модули

В отличие от C/C++ (компилятор, сборщик, пакетный менеджер — отдельные инструменты), в Go всё делает одна команда `go`:

```
go run      — скомпилировать и сразу запустить
go build    — собрать бинарник
go install  — собрать и положить в $GOBIN
go test     — запустить тесты
go fmt      — форматирование (gofmt)
go vet      — статический анализ
go mod      — работа с модулями
go get      — добавить зависимость
```

Про окружение достаточно знать три вещи:

- `GOROOT` — где установлен сам Go (не трогаем);
- `GOPATH` — историческое рабочее пространство; сегодня нужно в основном для `go install`-нутых инструментов. **Код проекта может лежать где угодно** — это частая путаница у читавших старые туториалы;
- `GOPROXY` — прокси для скачивания модулей (по умолчанию proxy.golang.org).

**Модуль** — единица версионирования, набор пакетов с корневым `go.mod`:

```bash
mkdir hello && cd hello
go mod init example.com/hello
```

```
module example.com/hello

go 1.22
```

`go get github.com/some/dep@v1.2.3` добавляет строку `require` в `go.mod`. Файл `go.sum` хранит контрольные суммы зависимостей — его не редактируют руками и не добавляют в `.gitignore`.

**Структура программы:**

```go
package main

import "fmt"

func main() {
	fmt.Println("Hello, World!")
}
```

Три момента, которые отличают Go от C/C++:

1. Точка входа — `package main` + `func main`. Аргументы командной строки в `main` не передаются — берите из `os.Args` или пакета `flag`.
2. Неиспользуемый импорт или локальная переменная — **ошибка компиляции**, а не warning. Чистота кода принудительная.
3. Открывающая `{` обязана стоять на той же строке — это требование парсера (из-за автоматической вставки `;`), а не вопрос стиля.

Бинарник получается самодостаточным: по умолчанию статическая линковка (для гарантии — `CGO_ENABLED=0 go build`), на целевой машине ничего ставить не нужно. Кросс-компиляция — одна переменная окружения:

```bash
GOOS=linux GOARCH=arm64 go build
```

## 1.3 Имена, переменные, константы, типы

**Видимость определяется регистром первой буквы.** `fmt.Println` экспортирован (большая `P`), всё, что начинается со строчной буквы, видно только внутри пакета. Никаких `public`/`private` — пакет является границей инкапсуляции (плюс механизм `internal/`, о нём ниже). Пакеты называют коротко, нижним регистром, без подчёркиваний: `fmt`, `strconv`, `httputil`.

**Нулевые значения.** В Go не бывает неинициализированных переменных — каждая получает нулевое значение своего типа:

```go
var x int    // 0
var s string // ""
var ok bool  // false
var p *int   // nil
var sl []int // nil
```

Это фундамент безопасности: класс C-багов «прочитали мусор из неинициализированной переменной» просто исчезает. Более того, нулевое значение стараются делать **полезным**: `bytes.Buffer{}` и `sync.Mutex{}` готовы к работе сразу, без конструктора.

Краткая форма `:=` объявляет переменную с выводом типа и работает только внутри функций:

```go
y := 10

in, err := os.Open(infile)
out, err := os.Create(outfile) // ок: err переиспользуется, in/out новые
f, err := os.Create(outfile)   // ошибка компиляции: нет новых переменных слева
```

Обмен значений — без временной переменной: `a, b = b, a`.

**Константы и iota:**

```go
const (
	Read    = 1 << iota // 1
	Write               // 2
	Execute             // 4
)

const GiB = 1 << 30 // untyped-константа: считается с произвольной точностью
```

`iota` — счётчик строк внутри `const`-блока (начинается с 0, сбрасывается в каждом блоке). Классическое применение — битовые флаги. Untyped-константы не имеют фиксированного типа, пока не использованы — поэтому `1 << 30` не переполняет ничего.

**Типы и преобразования.** `int` платформозависимый (64 бита на большинстве платформ), `byte` — алиас `uint8`, `rune` — алиас `int32` (кодовая точка Unicode, см. раздел про строки). Главный контраст с C++: **неявных приведений нет**:

```go
var i int = 42
var f float64 = float64(i) // компилятор молча ничего не делает — пишем сами
var u uint = uint(f)
```

Каждое преобразование явное: неудобно, зато ни одна конвертация не происходит «за спиной». Для строк и чисел — `strconv.Atoi("42")` (возвращает `(int, error)` — первый намёк на модель ошибок второй лекции) и `strconv.Itoa(42)`.

## 1.4 Управление потоком

```go
// if с инициализатором: v видна только внутри if/else
if v := compute(); v > 0 {
	fmt.Println("positive:", v)
}

// for — единственный цикл, четыре формы
for i := 0; i < 3; i++ {} // классический
for x < 10 { x *= 2 }     // как while
for {}                    // бесконечный
for i, ch := range "Go" {} // по слайсу/строке/мапе

// switch: break встроен, проваливания нет (есть явный fallthrough)
switch n := 2; n {
case 1, 2:
	fmt.Println("один или два")
default:
	fmt.Println("другое")
}

// безусловный switch — идиоматичная замена цепочки if/else if
switch {
case x < 0:
	fmt.Println("negative")
default:
	fmt.Println("positive")
}
```

Скобки вокруг условия не ставятся, фигурные — обязательны всегда. Идиому `if v := ...; cond` стоит полюбить сразу: она ограничивает область видимости и готовит к канону `if err != nil`.

## 1.5 Функции

**Множественный возврат** — примитив языка, и на нём построена вся модель ошибок:

```go
func divmod(a, b int) (int, int) {
	return a / b, a % b
}

q, r := divmod(17, 5) // 3 2
```

**Именованные возвраты** объявляют переменные результата в сигнатуре:

```go
func split(sum int) (x, y int) {
	x = sum * 4 / 9
	y = sum - x
	return // «голый» return
}
```

Плюс — самодокументация; минус — «голый» return в длинной функции прячет, что возвращается. Главная причина, почему именованные возвраты существуют, — модификация результата через `defer` (разберём на занятии 2 в теме `recover`).

**Вариативность:**

```go
func sum(nums ...int) int { // nums внутри — обычный []int
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

sum(1, 2, 3)
sum([]int{1, 2, 3}...) // развёртывание слайса
```

**Функции — значения первого класса.** С ними можно делать всё то же, что с числом: у функции есть тип (`func(int) int`), её можно присвоить переменной, передать, вернуть, хранить в мапе:

```go
type BinOp func(a, b int) int

ops := map[string]BinOp{
	"+": func(a, b int) int { return a + b },
	"-": func(a, b int) int { return a - b },
}
fmt.Println(ops["+"](2, 3)) // 5
```

Сравнивать функции можно только с `nil` (несравнимы между собой, ключами мапы быть не могут). Отсюда растут колбэки (`sort.Slice(s, less)`), `http.HandlerFunc`, middleware.

**Замыкания** — функция + захваченные переменные, захват всегда **по ссылке на переменную**:

```go
func counter() func() int {
	n := 0
	return func() int {
		n++
		return n
	}
}

c := counter()
fmt.Println(c(), c(), c()) // 1 2 3
fmt.Println(counter()())   // 1 — у нового замыкания своя n
```

Компилятор видит, что `n` переживает функцию (escape analysis), и кладёт её в кучу. То, что в C++ требует `shared_ptr` (иначе `[&n]` на локал — висячая ссылка), в Go работает «наивно» и безопасно. С Go 1.22 переменная цикла создаётся заново на каждой итерации, но понимать, что замыкание захватывает **переменную, а не значение**, по-прежнему обязательно.

**`defer`** откладывает вызов до выхода из функции — любым путём:

```go
func readFile(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close() // сразу после успешного захвата ресурса
	// ... много кода с ранними return
}
```

Три правила: несколько `defer` — LIFO; аргументы вычисляются **в момент объявления** (`i := 1; defer fmt.Println(i); i = 10` напечатает 1); это замена RAII — открыл ресурс, тут же написал `defer Close()`. Оверхед `defer` с Go 1.14 минимален (open-coded defers) — в горячем коде бояться его не нужно.

## 1.6 Пакеты, internal, init

- **Пакет** — каталог с `.go`-файлами с одинаковым `package name`. Порядок объявлений внутри пакета не важен, заголовочных файлов нет в принципе.
- **Модуль** — дерево пакетов под одним `go.mod`.

Импорты: псевдоним `import f "fmt"`; пустой импорт `import _ "image/png"` — ради побочных эффектов (регистрация декодера).

**`internal/`** — пакеты внутри `internal/` можно импортировать только из своего модуля и его поддерева, компилятор это проверяет. Инкапсуляция на уровне модуля.

**Порядок инициализации:** импортируемые пакеты (рекурсивно) → пакетные переменные → `init()` всех файлов пакета → `main()`. `init()` используют для регистрации (драйверы БД: `import _ "github.com/jackc/pgx/v5/stdlib"`). Сложную логику в `init` писать не стоит: её нельзя вызвать явно и нельзя вернуть из неё ошибку.

## 1.7 Срезы — главное, что нужно понять в Go

**Массивы** почти не используются напрямую: длина — часть типа (`[3]int` и `[4]int` — разные типы), массив передаётся по значению (копируется целиком). Всё внимание — срезам.

**Срез — это заголовок из трёх слов** над базовым массивом:

```
+--------+--------+--------+
|  ptr   |  len   |  cap   |
+--------+--------+--------+
     |
     v
[ data data data data ... ]
```

Следствия, которые надо понимать на уровне рефлексов:

1. Присваивание среза копирует заголовок, **но не данные** — два среза делят один массив.
2. Передача среза в функцию: функция может менять элементы, и это видно вызывающему.
3. `s[i]` паникует при `i >= len`, даже если `i < cap` — писать «за len» нельзя до ресайза.

**Создание:**

```go
var s []int               // nil-слайс: len=0, cap=0 — при этом рабочее значение
s1 := []int{1, 2, 3}
s2 := make([]int, 5)      // len=5, cap=5, нули
s3 := make([]int, 0, 10)  // len=0, cap=10
```

Разница nil-слайса и пустого `[]int{}` — только в сравнении `s == nil`; на практике её можно не различать.

**Срез-выражения — окна в массив:**

```go
s := []int{1, 2, 3, 4, 5}
sub := s[1:4] // [2 3 4], len=3, cap=4 — до конца базового массива!
```

`sub` делит память с `s`: `sub[0] = 100` изменит `s[1]`. Трёхиндексная форма `s[low:high:max]` ограничивает `cap`, отрезая возможность записи «за окно». По смыслу это `string_view` из C++17: не владеет, смотрит на чужое — и с теми же ловушками.

**`append` и рост capacity.** Если `len < cap`, `append` пишет в существующий массив; если места нет — аллокирует новый массив с запасом (удвоение примерно до 1024 элементов, дальше рост ~1.25x), копирует и возвращает **новый заголовок**. Поэтому железное правило: всегда `s = append(s, ...)` — забытая присваивание даёт невидимый баг. Рост хорошо виден в демо:

```go
var s []int
for i := 0; i < 8; i++ {
	s = append(s, i)
	fmt.Printf("len=%d cap=%d\n", len(s), cap(s))
}
// len=1 cap=1
// len=2 cap=2
// len=3 cap=4
// len=4 cap=4
// len=5 cap=8 ...
```

**Ловушка «append через окно»** — самый ценный пример темы:

```go
s := make([]int, 3, 6) // len=3, cap=6
copy(s, []int{1, 2, 3})

sub := s[:2]        // окно: len=2, cap=6, делит массив с s
_ = append(sub, 99) // пишет ЗА len(sub), но ВНУТРИ cap — в общий массив

fmt.Println(s) // [1 2 99] — s[2] затёрт!
```

Похожая ловушка — утечка памяти через под-срез: `header := data[:100]` от большого буфера держит весь буфер живым. Лечение — скопировать: `append([]byte(nil), data[:100]...)` или `slices.Clone`.

**`copy` и удаление:**

```go
dst := make([]int, len(src))
n := copy(dst, src) // min(len(dst), len(src)); корректна для перекрывающихся областей

s = append(s[:i], s[i+1:]...) // удаление i-го элемента с сохранением порядка
```

Современный пакет `slices` (Go 1.21+) покрывает типовые операции: `Contains`, `Index`, `Sort`, `Clone`, `Equal`.

## 1.8 Карты

```go
m := map[string]int{"a": 1, "b": 2}
m["c"] = 3

v, ok := m["x"] // comma ok: 0, false — «нет ключа» отличается от «значение 0»
delete(m, "a")

for k, v := range m { ... } // порядок итерации СЛУЧАЙНЫЙ (специально)
```

- Чтение из nil-мапы валидно (вернёт нулевое значение), **запись — паника**. Асимметрию надо запомнить.
- Ключ — любой сравнимый тип: числа, строки, структуры из сравнимых полей. Срезы, мапы, функции — нельзя (несравнимы).
- Мапа не потокобезопасна: конкурентный доступ — гонка (лекция 3, `-race`).

**Идиома «set»** — мапа с пустыми структурами:

```go
set := map[string]struct{}{}
set["x"] = struct{}{}
_, exists := set["x"]
delete(set, "x")
```

`struct{}` имеет размер 0 — тратим память только на ключи. Аналог `std::unordered_set`.

## 1.9 Строки, руны и байты

**Строка — иммутабельный срез байт**, а литералы и исходники — UTF-8. Чтобы тема «щёлкнула», разделите три понятия: **байт** (единица памяти), **руна** (кодовая точка Unicode, `int32`) и **графема** (то, что видит человек).

UTF-8 — переменная длина:

```
0xxxxxxx                              1 байт,  0–127 (ASCII)
110xxxxx 10xxxxxx                     2 байта, кириллица, греческий
1110xxxx 10xxxxxx 10xxxxxx            3 байта, CJK
11110xxx 10xxxxxx 10xxxxxx 10xxxxxx   4 байта, эмодзи и прочее
```

Важные свойства: ведущий байт задаёт длину; кодировка самосинхронизирующаяся (границу символа можно найти с любого байта); ASCII — подмножество; порядок байтов совпадает с порядком кодовых точек (сортировка работает без декодирования). UTF-8 придумали Томпсон и Пайк — поэтому в Go она «родная».

```go
s := "мир"
fmt.Println(len(s))                    // 6 — байты, не символы!
fmt.Printf("% x\n", s)                 // d0 bc d0 b8 d1 80
fmt.Println(utf8.RuneCountInString(s)) // 3

for i, r := range s { // range — встроенный UTF-8-декодер
	fmt.Printf("%d: %c\n", i, r)
}
// 0: м
// 2: и   — индексы БАЙТОВ, поэтому не подряд
// 4: р
```

`len(s)` — O(1) (байты), `utf8.RuneCountInString(s)` — O(n) (руны). Некорректный байт декодируется в `U+FFFD` — программа не падает. Преобразования `string ↔ []byte` и `[]rune(s)` копируют данные — в цикле конкатенацию не делайте (O(n²)), используйте `strings.Builder`.

**Графемы.** Эмодзи «семья» 👨‍👩‍👧 — это 3 эмодзи + 2 Zero Width Joiner: 18 байт, 5 рун, но 1 графема. `len` вернёт 18, `RuneCountInString` — 5, а «символов» человек увидит один. Сегментация на графемы — отдельная задача (`golang.org/x/text`).

## 1.10 Структуры и указатели

```go
type Point struct{ X, Y int }

p := Point{1, 2}          // позиционная форма
p2 := Point{X: 1, Y: 2}   // именованная — предпочтительно
pp := &Point{X: 1}        // сразу *Point
```

Неуказанные поля получают нулевые значения; структуры сравнимы, если сравнимы все поля; присваивание — побитовая копия.

**Указатели** — как в C (`&`, `*`), но **без арифметики**: это фундамент memory safety. Возвращать адрес локальной переменной — легально и идиоматично:

```go
func NewPoint() *Point {
	p := Point{1, 2} // escape analysis: p «убегает» в кучу
	return &p
}
```

В C++ это UB; в Go компилятор сам решает, где живёт переменная, а GC не даст ей умереть раньше времени. `new`/`delete` не нужны.

**Семантика передачи** — таблица, которую стоит запомнить:

| Тип | При передаче | Делятся ли данные |
|---|---|---|
| массив, структура | копия целиком | нет |
| срез, мапа, канал, строка, функция | копия заголовка | да! |

## 1.11 Методы

Метод — функция с ресивером. Ресивер пишется перед именем; `this`/`self` нет, конвенция — короткое имя от типа:

```go
func (p Point) Distance() float64 { // ресивер-значение: работает с копией
	return math.Sqrt(float64(p.X*p.X + p.Y*p.Y))
}

func (p *Point) Move(dx, dy int) { // ресивер-указатель: мутирует оригинал
	p.X += dx
	p.Y += dy
}
```

Методы можно определять только для типов своего пакета. Правила выбора ресивера:

- мутирует состояние → указатель;
- большая структура → указатель (чтобы не копировать);
- если хоть один метод на указателе — делайте **все** на указателе (консистентность).

Важно на будущее: метод с ресивером-указателем входит в метод-набор `*T`, но **не** `T` — это станет критичным при интерфейсах.

## 1.12 Встраивание вместо наследования

```go
type Animal struct{ Name string }

func (a Animal) Speak() { fmt.Println(a.Name) }

type Dog struct {
	Animal // анонимное поле — встраивание
	Breed  string
}

d := Dog{Animal: Animal{Name: "Рекс"}, Breed: "labrador"}
d.Speak()        // метод «поднялся»
d.Animal.Speak() // оригинал тоже доступен
```

Под капотом никакой магии: компилятор генерирует обёртки-делегаты, `d.Speak()` — это `d.Animal.Speak()`. Нет таблицы виртуальных методов и нет `super`. Определение `func (d Dog) Speak()` **перекрывает** (не переопределяет!) метод: `Animal.Speak()` не становится виртуальным и не «видит» перекрытий. Встраивать можно структуры, указатели и интерфейсы (последнее — способ дать «дефолтную реализацию» части методов).

**Теги полей** — строки-метаданные, читаемые через `reflect` (подробно — на занятиях 5 и 9):

```go
type User struct {
	ID    int    `json:"id"`
	Email string `json:"email,omitempty"`
	Pass  string `json:"-"`
}
```

# Занятие 2. Интерфейсы и обработка ошибок

## 2.1 Интерфейс: набор методов и неявное удовлетворение

Интерфейс — это **набор методов**, ничего больше: ни полей, ни реализации.

```go
type Speaker interface{ Speak() string }

type Dog struct{}
type Cat struct{}

func (Dog) Speak() string { return "Гав" }
func (Cat) Speak() string { return "Мяу" }

func greet(s Speaker) { fmt.Println(s.Speak()) } // не знает ни о Dog, ни о Cat

func main() {
	greet(Dog{}) // Гав
	greet(Cat{}) // Мяу
}
```

Ключевое отличие от C++/Java: тип **не объявляет**, какие интерфейсы реализует. Тип удовлетворяет интерфейсу, если реализует все его методы, — «duck typing», проверенный компилятором статически. Следствия:

- зависимость обратная: `Dog` ничего не знает о `Speaker`;
- можно удовлетворить интерфейс, написанный **после** вашего типа и в чужом пакете;
- `greet` не меняется при добавлении новых типов — полиморфизм без иерархий.

Идиома явной проверки на этапе компиляции (конвенция stdlib):

```go
var _ Speaker = Dog{} // не скомпилируется, если Dog не реализует Speaker
```

## 2.2 `any`: откуда он взялся и чем платим

Специального типа «любое значение» в Go нет — им служит **пустой интерфейс** `interface{}`, то есть интерфейс без методов. Это не спец-механизм, а вырожденный случай неявного удовлетворения: интерфейс не требует ни одного метода — ему удовлетворяет **любой** тип.

До Go 1.18 это был единственный способ написать «принимаю что угодно» (`fmt.Println(args ...interface{})`, JSON в `map[string]interface{}`). Проблемы: читается тяжело (особенно `[]map[string]interface{}`), намерения не выражает, и его тащили туда, где нужны были дженерики. Поэтому в 1.18 вместе с дженериками добавили алиас:

```go
type any = interface{}
```

Это чистый синоним: никакой новой семантики, старый код менять не нужно. Смысл — читабельность и честность: `any` говорит «я осознанно принимаю любое значение». А появление одновременно с дженериками не случайно: теперь выбор есть (конкретный тип / маленький интерфейс / дженерик), и `any` — осознанное решение, а не «иначе никак».

Цена: статическая проверка типов выключена — все проверки уезжают в рантайм (через type assertion/switch, см. ниже). Ориентир для C++: `std::any` (или `void*` в C), только наш `any` — это пара «(тип, значение)» (см. 2.4) и без вопросов о времени жизни благодаря GC. Мы уже пользовались `any` не замечая: `errors.As(err, &pathErr)` имеет сигнатуру `As(err error, target any)`.

## 2.3 Type assertion и type switch

**Assertion** — утверждение «внутри лежит вот такой тип». Компилятор проверить его не может — тип в интерфейсе известен только в рантайме:

```go
var i any = "hello"

s, ok := i.(string) // безопасная форма: "hello", true
n, ok := i.(int)    // 0, false
v := i.(int)        // ПАНИКА: interface conversion
```

Форма без `ok` — только когда тип гарантированно известен. Аналог `dynamic_cast`, но встроен в язык и не бросает исключение в ok-форме.

**Type switch** — единственный нормальный способ ветвления по динамическому типу:

```go
func describe(i any) {
	switch v := i.(type) {
	case string:
		fmt.Println("string:", v) // v здесь — string
	case nil:
		fmt.Println("nil")
	default:
		fmt.Printf("unknown: %T\n", v)
	}
}
```

Внутри `case` одного типа переменная `v` автоматически типизирована. Отдельный `case nil` не случаен — про это следующий раздел.

## 2.4 Интерфейс под капотом и главная ловушка

Значение интерфейса — **пара из двух слов**:

```
+--------------+---------------+
|  type (itab) |  value (data) |
+--------------+---------------+
```

`type` — дескриптор динамического типа с таблицей методов, `value` — указатель на данные. Интерфейс равен `nil` тогда и только тогда, когда **оба** поля нулевые. Отсюда классическая ловушка:

```go
type Seller interface{ GetID() int64 }
type Store struct{}

func (st *Store) GetID() int64 { return 1 }

func main() {
	var seller Seller // (nil, nil)
	fmt.Println(seller == nil) // true

	var store *Store // nil, но тип уже есть
	seller = store   // (*Store, nil)
	fmt.Println(seller == nil) // false — типизированный nil!
}
```

Разбор: мы положили в интерфейс nil-указатель конкретного типа. Поле `type` заполнилось (`*Store`), поле `value` осталось nil — интерфейс перестал быть «пустым», сравнение с `nil` даёт false. Правило: функция, возвращающая интерфейс, должна возвращать **литеральный** `nil`, а не типизированный nil-указатель:

```go
func doWork() Speaker {
	var r *Robot // nil
	return r     // БАГ: doWork() != nil
	// правильно: return nil
}
```

Эта же ловушка ждёт в модели ошибок: `var err error` + `err = f()` где `f` вернула `(*MyError)(nil)` — и `err != nil`, хотя ошибки «нет».

## 2.5 Композиция интерфейсов и идиомы

Интерфейсы встраиваются друг в друга, объединяя наборы методов:

```go
type ReadWriter interface {
	Reader
	Writer
}
```

Любой тип, реализующий оба, автоматически реализует `ReadWriter`. Так устроены `io.ReadWriter`, `io.ReadWriteCloser` и т.д.

Четыре идиомы, которые стоит унести с собой:

1. **Принимай интерфейс, возвращай структуру.** Параметр-интерфейс даёт слабую связанность (легко подставить мок в тесте), возврат-структура — все поля и методы у пользователя. Возврат интерфейса заставляет его идти в type switch за данными.
2. **Размер интерфейса — 1–3 метода.** Большой интерфейс труднее реализовать и замокать.
3. **Определяй интерфейс у потребителя, а не у реализации.** «Что мне нужно от хранилища» описывается в терминах моей логики, а не в пакете хранилища — это прямое следствие неявного удовлетворения.
4. **Не злоупотребляй `any`** — сначала дженерик (занятие 5), потом `any`.

Примеры из stdlib, которые вы будете встречать постоянно: `error` (`Error() string`), `fmt.Stringer` (`String() string`), `io.Reader`/`io.Writer`, `sort.Interface`, `http.Handler`. Сила маленьких интерфейсов видна в `io.Copy(dst, src)`: одна функция копирует файл в сеть, HTTP-ответ в буфер, буфер в файл — из *чего угодно* в *куда угодно*.

Демонстрация `fmt.Stringer` — «магия» fmt оказывается обычным type assertion внутри библиотеки:

```go
type Money int64 // копейки

func (m Money) String() string {
	return fmt.Sprintf("%d.%02d ₽", m/100, m%100)
}

fmt.Println(Money(1500)) // 15.00 ₽ — fmt сам вызвал String()
```

## 2.6 Ошибка как значение

В Go нет исключений — и это осознанная сделка:

- `try/catch` создаёт невидимые пути управления: неизвестно, где вылетит и что будет после;
- ошибка-значение делает путь ошибок явным: `return err` видно в коде;
- сигнатура честно сообщает «может не удаться».

Платой признаём многословность `if err != nil` — она повторяется тысячи раз, но путь исполнения линеен и предсказуем.

Сам `error` — **встроенный интерфейс**:

```go
type error interface {
	Error() string
}
```

Всё, что имеет метод `Error() string`, — ошибка. Прямое применение всей теории интерфейсов.

Базовая идиома:

```go
func loadConfig(path string) (*Config, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, err
	}
	// ...
}

cfg, err := loadConfig("config.json")
if err != nil {
	log.Fatal(err)
}
```

Чек-лист: `error` — последний возвращаемый результат; при `err != nil` остальные значения считаются мусором; не игнорируйте ошибку через `_` без осознанной причины; текст ошибки — с маленькой буквы, без точки (ошибки компонуются в цепочки: `open config: no such file`); сообщение описывает *что* не удалось, контекст добавляют обёртки.

## 2.7 Сторожевые (sentinel) ошибки

Некоторые ошибки — не текст, а **сигнал**, на который код реагирует по-разному (404, retry, конец чтения). Их оформляют пакетными переменными:

```go
var ErrNotFound = errors.New("not found")
```

- Сравнение — по **identity**, а не по тексту: одинаковый текст в двух пакетах — разные ошибки.
- `errors.New` возвращает указатель на неэкспортируемую структуру — каждый вызов даёт уникальное значение.
- Конвенции: `Err`-префикс для переменных, `Error`-суффикс для типов.
- Из stdlib: `io.EOF` (штатный «конец данных», а не сбой), `sql.ErrNoRows`, `http.ErrServerClosed`.

Важный мостик: как только ошибку обернули, сравнение `err == ErrNotFound` перестаёт работать — нужна `errors.Is` (2.9).

## 2.8 Оборачивание через `%w`

Два наивных варианта плохи: голый `return err` теряет контекст (наверх прилетает `sql: no rows` без деталей), а `fmt.Errorf("...: %v", err)` даёт контекст, но превращает ошибку в строку. Третий путь:

```go
func service() error {
	if err := repo(); err != nil {
		return fmt.Errorf("load user: %w", err)
	}
	return nil
}

func main() {
	err := service()
	fmt.Println(err)                         // load user: not found
	fmt.Println(errors.Is(err, ErrNotFound)) // true — %w сохранил цепочку
}
```

`%w` сохраняет исходную ошибку **внутрь** новой — получается цепочка `handle request → load user → not found`. Текст печатается целиком, а код наверху может «прощупать» причину. `%v`/`%s` — только текст: вывод выглядит так же, но `errors.Is` вернёт false — классическая ошибка новичков. С Go 1.20 можно оборачивать несколько ошибок — несколько `%w` в одном `fmt.Errorf`. Гигиена: каждый слой добавляет только свой контекст (операция, путь, id), не пересказывая причину снизу.

## 2.9 `errors.Is` и `errors.As`

`errors.Is` идёт по цепочке: сравнивает ошибку с целью на равенство, делает `Unwrap()` и повторяет. Отвечает на вопрос «есть ли в цепочке эта причина?»:

```go
if errors.Is(err, sql.ErrNoRows) {
	// «нет такого пользователя» — вернуть 404
}
```

Наивное `err == sql.ErrNoRows` ломается при первом же оборачивании. Проверять текст через `strings.Contains` — антипаттерн (хрупко, ломается при рефакторинге сообщений). Типичная «маршрутизация» по сигналам: не найдено → 404, таймаут → retry, `context.Canceled` → клиент ушёл.

`errors.As` — type assertion по цепочке: ищет первую ошибку нужного типа и записывает её в переменную:

```go
var pathErr *fs.PathError
if errors.As(err, &pathErr) {
	fmt.Println(pathErr.Path) // данные конкретного типа
}
```

Реальный пример: `os.ReadFile` возвращает `*fs.PathError` с полями `Op`, `Path`, `Err`. Амперсанд обязателен — передаём, куда записать результат.

Формула: **`Is` — «это она?» (сравнение со сторожевым значением), `As` — «дай её мне» (извлечение типа с данными).**

## 2.10 `errors.Join` — собрать все ошибки сразу

До этого сценарий был «одна причина». Для валидации нужен обратный — все проблемы за один заход:

```go
func validateForm(email string, age int) error {
	var errs []error
	if email == "" {
		errs = append(errs, errors.New("email: required"))
	}
	if age < 18 {
		errs = append(errs, errors.New("age: must be 18+"))
	}
	return errors.Join(errs...) // nil, если errs пуст
}

fmt.Println(validateForm("", 15))      // email: required
                                       // age: must be 18+
fmt.Println(validateForm("a@b.c", 20)) // <nil>
```

Join печатает ошибки в столбик и участвует в цепочке `Unwrap` (у него несколько «родителей» — `Unwrap() []error`, поэтому `Is`/`As` ищут в каждой из склеенных). Ключевая фишка — nil-семантика: `Join()` без аргументов возвращает `nil`, поэтому паттерн валидации сжимается в одну строку без единого `if err`.

## 2.11 `errors.Unwrap` — как всё устроено внутри

Вся система ошибок держится на трёх маленьких интерфейсах:

```go
Unwrap() error          // один «родитель» — обычная цепочка: %w, *fs.PathError
Unwrap() []error        // несколько «родителей» — errors.Join
Is(target error) bool   // кастомное сравнение внутри errors.Is
```

`errors.Is` — просто цикл поверх них, никакой магии:

```go
for err != nil {
	if err == target {
		return true
	}
	err = errors.Unwrap(err)
}
```

Напрямую `Unwrap` в прикладном коде почти не нужен, но цикл стоит понимать.

## 2.12 Кастомные типы ошибок

Развилка: нужен только **сигнал** — сторожевая переменная; нужны **данные** (какое поле, какой код, какой путь) — свой тип:

```go
type ValidationError struct {
	Field   string
	Message string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("field %q: %s", e.Field, e.Message)
}

func validate(u User) error {
	if u.Email == "" {
		return &ValidationError{Field: "email", Message: "required"}
	}
	return nil
}

var ve *ValidationError
if errors.As(err, &ve) {
	fmt.Println(ve.Field) // "email"
}
```

`*fs.PathError` из stdlib — точно такая же конструкция, плюс метод `Unwrap()` до внутренней причины: свой тип может встраиваться в цепочки, и его находит `errors.As` сквозь слои. Полный жизненный цикл одной ошибки: создать (`&ValidationError{...}`) → проверить (`errors.As`) → прочитать данные (`ve.Field`) → отдать текст (`err.Error()`) → обернуть дальше (`fmt.Errorf("register: %w", err)`).

## 2.13 `panic` и `recover`

`panic` — аварийная раскрутка стека. Семантика: «нарушен инвариант, дальше работать нельзя». Легитимные паники — runtime-ошибки (выход за границы, nil-разыменование) и `panic("unreachable")` в недостижимой ветке. Паника вместо `err != nil` — антипаттерн.

`recover` останавливает панику, но работает **только внутри отложенной функции**:

```go
func safeCall() (result int, err error) {
	defer func() { // именованные возвраты: defer дописывает err
		if r := recover(); r != nil {
			err = fmt.Errorf("panic: %v", r)
		}
	}()
	panic("something impossible")
}

func main() {
	res, err := safeCall()
	fmt.Println(res, err) // 0 panic: something impossible
}
```

Разбор: паника раскручивает стек, отложенная функция выполняется «по пути», `recover` гасит панику, а через именованный возврат функция возвращает ошибку как ни в чём не бывало.

Где это уместно: HTTP-сервер (`net/http` ловит паники в обработчиках из коробки, но middleware-паттерн стоит знать — он везде во фреймворках), границы доверия (плагины, обёртки над reflect). Где нет: вместо `error` — теряется читаемость, статически не проверить.

Реальный middleware:

```go
func Recover(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				log.Printf("panic: %v\n%s", rec, debug.Stack())
				http.Error(w, "internal server error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```

## 2.14 `defer`: что добавилось после занятия 1

Повторение: несколько `defer` — LIFO; аргументы вычисляются в момент объявления (`i := 1; defer fmt.Println(i); i = 10` напечатает 1); выполняется при любом выходе. Новое — три акцента.

**Как работает `return`.** Это три шага: присвоить значения результатам → выполнить отложенные функции → выйти. Значит, отложенная функция видит результат до выхода и может его переписать:

```go
func f() (x int) {
	defer func() { x++ }()
	return 41 // x = 41 → defer сделал 42 → вызывающий получит 42
}
```

На этом же стоит `recover` (см. 2.13): `safeCall` — тот же трюк, что и `x++`, только вместо инкремента — запись ошибки.

**Cleanup с ошибкой.** Ошибку `Close()` игнорировать привычно, но у файла на запись она реальна (сброс буферов, место на диске). Паттерн с `errors.Join` — ошибка закрытия не теряется и не затирает ошибку записи:

```go
func writeConfig(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() { err = errors.Join(err, f.Close()) }()

	_, err = f.Write(data)
	return err
}
```

**`defer` живёт до конца функции, а не блока.** `defer f.Close()` внутри цикла накопит все закрытия до выхода из функции: десять тысяч итераций — десять тысяч открытых дескрипторов. Лечение — вынести тело итерации в функцию или закрывать явно.

# Шпаргалка: что должно остаться в голове

Занятие 1:

1. Срез = `(ptr, len, cap)`; `append` возвращает новый заголовок; данные делятся между срезами.
2. Строка — байты в UTF-8; `rune` — кодовая точка; графема — не то же самое.
3. Видимость — по регистру первой буквы; граница — пакет.
4. Нулевые значения полезны; неявных приведений типов нет.
5. Ресивер-указатель для мутации; консистентность ресиверов.
6. Встраивание — композиция с делегированием, не наследование.
7. `defer` сразу после захвата ресурса.

Занятие 2:

1. Удовлетворение интерфейса неявное и проверяется компилятором; `var _ I = T{}`.
2. Интерфейс — пара `(type, value)`; типизированный nil — не nil.
3. Маленькие интерфейсы у потребителя; принимать интерфейс — возвращать структуру.
4. `error` — интерфейс; ошибка — значение; `if err != nil` — явный путь исполнения.
5. `%w` оборачивает, `%v` — нет; `Is` — «это она?», `As` — «дай её мне».
6. `panic` — для инвариантов, `recover` — на границах, не для бизнес-ошибок.

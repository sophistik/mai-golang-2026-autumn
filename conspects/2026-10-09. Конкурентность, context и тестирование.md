# Конспект занятий 3–4: конкурентность, context и тестирование

# Занятие 3. Горутины, каналы, sync и context

## 3.1 Горутины — просто `go`

```go
go doWork() // запуск и немедленное продолжение
```

Горутина — функция, запущенная конкурентно. Никаких дескрипторов, `pthread_create`, `join` — слово `go` и всё. Контраст с C: `pthread_create` требует настройки атрибутов и вручную ждёт завершения через `pthread_join`; здесь «тредов» в явном виде нет вообще.

Три факта, которые надо усвоить сразу:

1. **`main` не ждёт горутины.** Выход из `main` завершает **все** горутины мгновенно. `time.Sleep` в демо — костыль «только для демо»; правильное ожидание — `sync.WaitGroup`.
2. **Порядок вывода горутин недетерминирован** — прогоните пример несколько раз.
3. **Паника в горутине валит весь процесс** (см. 3.2 в конце раздела).

## 3.2 Горутины дёшевы: стек и его рост

Стартовый стек горутины — **~2 КБ** (тред ОС — мегабайты), поэтому «миллион горутин» — рабочая история: по горутине на соединение или запрос.

Как стек растёт: точка роста — **пролог каждой функции**. Компилятор вставляет проверку «влезает ли кадр»; не влезает — рантайм выделяет новый стек **вдвое больше**, копирует содержимое и корректирует указатели (в C двигать стек нельзя — там адреса локалов «сырые»; в Go компилятор знает все указатели). Сжатие — при GC: занята меньше четверти — стек урезают вдвое. Потолок — **1 ГБ**: дальше `fatal error: stack overflow`, это не паника и `recover`'ом не ловится. Бесконечная рекурсия умирает с честным дампом стека — в C она была бы segfault или тихой порчей памяти.

## 3.3 Планировщик GMP и вытеснение

Модель **GMP**: **G** — горутина, **M** — тред ОС, **P** — логический процессор (их количество = `GOMAXPROCS`). У каждого P своя локальная очередь горутин; освободившийся M берёт работу оттуда, а если пусто — «ворует» половину чужой очереди (work stealing) или идёт в глобальную очередь.

Планировщик **кооперативный**: горутина отдаёт управление в известных точках — операции с каналами, `time.Sleep`, аллокации, syscalls, пролог функции. А с **Go 1.14** есть и асинхронное вытеснение: фоновый поток **sysmon** замечает горутину, работающую дольше **10 мс**, и прерывает её сигналом `SIGURG`. Плотный `for {}` больше не держит ядро вечно.

`GOMAXPROCS` — количество P. Дефолт — число логических ядер. Задать больше, чем ядер, — не ускорить, а добавить переключений контекста. Ловушка k8s: до Go 1.25 рантайм видел ядра **хоста**, а не CPU-лимит пода — при лимите в 1 ядро и 64 P контейнер получал CFS-троттлинг (латентность скачет пиками при низкой средней загрузке). Лечение: Go 1.25+ учитывает cgroup сам; раньше — `import _ "go.uber.org/automaxprocs"` или ручной `GOMAXPROCS`.

## 3.4 Паника в горутине

Паника раскручивает стек **своей** горутины; непойманная — падает весь процесс. Два момента, которые путают:

- **`defer` при панике работает** — раскрутка стека выполняет отложенные функции (иначе `recover` не имел бы смысла);
- **`recover` из чужой горутины не работает**: у каждой горутины свой стек и своя цепочка `defer`. `recover` в `main` не спасает от паники в дочерней горутине.

Правило: каждая горутина сама отвечает за свой `recover`. Так устроены HTTP-серверы — на каждую горутину-запрос свой middleware с recover.

## 3.5 Happens-before: когда записи видны

Центральный вопрос конкурентности: когда одна горутина **гарантированно видит** записи другой? Интуиция «по часам» не работает — регистры, кеши, переупорядочивание.

**Ребро happens-before**: «A happens-before B» = эффект A гарантированно виден в B. Это не про время — про видимость.

```
A: n = 42
A: ch <- n ──happens-before──> B: v := <-ch
                               B: print(v)  // 42 — всегда
```

**Гонка данных** — два доступа к одной памяти, хотя бы один — запись, и между ними **нет ребра**. Известные рёбра: внутри одной горутины (как написано), `go f()` → первая инструкция горутины, `WaitGroup.Done` → возврат из `Wait`, отправка в канал → приём, `close` → приём нулевого значения, `Mutex.Unlock` → следующий `Lock`, `Once.Do` → возвраты остальных, atomic-операции над одним адресом. Ребро транзитивно. Хотите читать чужое — постройте ребро.

## 3.6 WaitGroup

```go
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
	wg.Add(1)            // ДО запуска горутины
	go func() {
		defer wg.Done()  // первой строкой в горутине
		work()
	}()
}
wg.Wait()
```

Канон: `Add` до `go`, `defer Done` первой строкой, `Wait` в точке встречи. `Add` **внутри** горутины — гонка: `Wait` может пройти раньше, чем `Add` выполнится. Ребро `Done → Wait` гарантирует: все записи горутины видны дождавшемуся.

## 3.7 Каналы

Канал — **типизированная труба**: `make(chan string)`. Отправка `ch <- v`, приём `v := <-ch`. Обе операции **блокируют**: небуферизованный канал — рандеву, отправка не завершится, пока кто-то не заберёт.

Главная мысль: канал передаёт одновременно **данные и синхронизацию** — отправка happens-before завершение приёма, значение приезжает со всеми побочными эффектами. Это и есть лозунг Go: *«Не общайтесь через разделяемую память; делитесь памятью, общаясь»*.

**Буферизованный** `make(chan int, 2)` — очередь: запись блокируется при полном буфере, чтение — при пустом. `len(ch)`/`cap(ch)` — для отладки.

**Закрытие**: `close(ch)` — протокол «данных больше не будет»; закрывает **отправитель**, приёмник закрыть нельзя. `for v := range ch` читает до закрытия. Чтение из закрытого канала возвращает нулевое значение (`ok == false`) и **не паникует** — можно молча обработать мусор; паникует только **отправка** в закрытый. Двойной `close` — тоже паника.

**Направления**: `chan<- int` — только отправка, `<-chan int` — только приём. Функции-производители возвращают `<-chan T` — контракт «только чтение».

**nil-канал** (нулевое значение): отправка и приём блокируются навсегда. Забыли `make` — тихий дедлок. В `select` ветка на nil-канале никогда не срабатывает — этим иногда сознательно «выключают» ветку.

**select** — мультиплексирование: ждёт на нескольких каналах, срабатывает готовая ветка; готовых несколько — выбор **случайный** (анти-голодание). `time.After(d)` — канал-таймаут. Ветка `default` делает select неблокирующим — идиомы try-send/try-recv; но busy-loop на default сжигает CPU.

Если **все** горутины спят — runtime печатает `fatal error: all goroutines are asleep - deadlock!` со стеками. Дедлок на каналах обнаруживается сам; дедлок на мьютексах — нет.

## 3.8 Гонки данных и `-race`

`n++` — три шага (прочитать, сложить, записать); две горутины перемешиваются — инкременты теряются. Гонка — не «редкая ошибка», а гарантированный баг, который ещё не проявился.

```bash
go run -race .
go test -race
```

`-race` — динамический детектор: ловит **фактически случившиеся** гонки и печатает оба стека (запись и чтение). Без детектора программа «работает» — просто врёт. Правило курса: тесты всегда с `-race`. В проде детектор дорог (память/CPU) — им ловят на CI. Помните: детектор находит только гонки, которые случились на прогоне, — нужно покрытие.

## 3.9 sync: Mutex, RWMutex, Once, Pool, atomic

**`sync.Mutex`** — взаимное исключение. Мьютекс объявляют **рядом с защищаемыми данными**; `defer mu.Unlock()` при ранних выходах. Не рекурсивен (двойной `Lock` — дедлок), копировать нельзя (go vet ловит) — методы с мьютексом живут на указателе. Ребро: `Unlock` happens-before следующий `Lock`.

**`sync.RWMutex`** — много `RLock` ИЛИ один `Lock`. Выигрыш — только при «много читателей + редкая запись + **долгое** чтение»: каждый `RLock` — атомарная правка одного счётчика, короткие секции выстраиваются в конвейер. Решать бенчмарком, не интуицией.

**`sync.Once`** — ленивая инициализация ровно один раз:

```go
var (
	once   sync.Once
	config *Config
)

func GetConfig() *Config {
	once.Do(func() { config = loadConfig() })
	return config
}
```

Остальные горутины **ждут завершения** `f`. Нюансы: паника в `f` считается выполнением (повторов не будет); «сбросить» нельзя.

**`sync.Pool`** — переиспользование временных объектов (буферы, энкодеры) ради меньшего давления на GC. GC может выбросить содержимое в любой момент → это **только кеш**, не хранилище; перед `Put` — `Reset()`.

**`sync/atomic`** — счётчики и флаги одной инструкцией: `var hits atomic.Int64; hits.Add(1)`. CAS-цикл — «оптимистическая» конкуренция. Граница: атомик защищает **одно значение**; инвариант на несколько полей — только мьютекс.

## 3.10 errgroup и singleflight

**`errgroup`** (`golang.org/x/sync/errgroup`) — WaitGroup, который собирает **первую ошибку** и отменяет остальных:

```go
g, ctx := errgroup.WithContext(ctx)
for _, url := range urls {
	g.Go(func() error { return fetch(ctx, url) })
}
if err := g.Wait(); err != nil {
	return err // первая ошибка; ctx уже отменён
}
```

`g.SetLimit(n)` ограничивает параллелизм — часто заменяет ручной worker pool. Ошибки не нужны — plain WaitGroup проще.

**`singleflight`** — дедупликация одновременных одинаковых вызовов (cache stampede: тысяча запросов при истёкшем кеше → один поход в БД): `group.Do(key, fn)` выполняет `fn` один раз, остальные по ключу получают готовый результат. Результат общий — мутировать его нельзя.

## 3.11 Паттерны

**Генератор** — горутина + канал как источник:

```go
func nums() <-chan int {
	out := make(chan int)
	go func() {
		for i := 1; ; i++ {
			out <- i
		}
	}()
	return out
}
```

Обязательный разбор: когда потребитель перестал читать, горутина навсегда висит на `out <- i` — **утечка горутины**. Лечение — отмена через `select`/`ctx.Done()`.

**Pipeline** — стадии-горутины, соединённые каналами: каждая читает вход, преобразует, пишет в выход и делает `close(out)` по завершении входа. Стадии работают параллельно; завершение распространяется закрытием по цепочке.

**Worker pool** — N воркеров читают один канал задач; кто свободен, тот взял. Завершение: `ctx.Done()` в `select` + закрытие канала задач + `wg.Wait()` + `close(results)`.

**Fan-out/fan-in** — масштабирование стадии: N обработчиков читают один вход; выходы сливаются `merge`'ом (WaitGroup по источникам → `close(out)`). Порядок после merge недетерминирован.

## 3.12 context

```go
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel() // всегда, даже после успеха

select {
case res := <-workCh:
case <-ctx.Done():
	return ctx.Err() // context.DeadlineExceeded
}
```

Отмена **кооперативная**: контекст не останавливает горутину — он сообщает через `ctx.Done()` (закрытый канал), а горутина проверяет его в точках ожидания. `WithTimeout` — отмена по расписанию (`Err()` станет `DeadlineExceeded`). `cancel` идемпотентен, но вызвать обязаны — иначе утечка таймера (go vet: lostcancel).

Правила: `ctx` — **первый** параметр; корень `context.Background()` — в `main`/тестах; `WithValue` — только request-scoped инфраструктура (trace id); контекст не хранят в структурах.

**Graceful shutdown**: сигнал (`SIGTERM` от docker/k8s) → `signal.NotifyContext` → контекст отменён → горутины выходят по `Done()` → `wg.Wait()` → закрыть ресурсы → выход. SIGKILL (9) не перехватывается. На остановку ставят дедлайн, чтобы зависший воркер не держал процесс вечно.

# Занятие 4. Тестирование, бенчмарки и тулинг

## 4.1 Первый тест

Тест — обычная функция с особым именем. Формальные требования, на которых спотыкаются все:

1. **Файл — `*_test.go`**: `go test` читает только их, `go build` игнорирует. Опечатка в суффиксе — тесты молча не запустятся.
2. **Функция — `TestXxx(t *testing.T)`**: префикс `Test` и первый символ после него **не строчная** (`TestDiv` ок, `Testdiv` молча игнорируется).
3. **Пакет — тот же** (или внешний `foo_test` — тогда только экспортированное).
4. **Никакой регистрации** — `go test ./...` находит сам. Ни классов, ни TestCase, как в C++.

```go
func TestDiv(t *testing.T) {
	got, err := Div(10, 2)
	if err != nil {
		t.Fatalf("unexpected err: %v", err)
	}
	if got != 5 {
		t.Errorf("Div(10, 2) = %d; want 5", got, err)
	}
}
```

`-v` — подробный вывод; убедиться, что тест нашёлся.

## 4.2 Errorf vs Fatalf

- `t.Errorf` — пометить провал и **продолжить**: соберём все падения за один прогон.
- `t.Fatalf` — провал и **немедленный выход** (внутри `Logf` + `FailNow` через `runtime.Goexit`).

Правило: проверка, на которой держится весь дальнейший код (`err != nil`, объект не nil), — `Fatalf`; независимые проверки — `Errorf`. Оба останавливают только текущий тест. Формат сообщений — `got ... want ...`.

## 4.3 Табличные тесты

Канонический идиом Go — слайс анонимных структур + цикл:

```go
tests := []struct {
	name string
	a, b int
	want int
}{
	{"positive", 10, 2, 5},
	{"negative", -10, 2, -5},
	{"by zero", 10, 0, 0},
}
for _, tt := range tests {
	if got, _ := Div(tt.a, tt.b); got != tt.want {
		t.Errorf("%s: Div(%d, %d) = %d; want %d", tt.name, tt.a, tt.b, got, tt.want)
	}
}
```

Новый кейс = новая строка таблицы — тесты перестают быть копипастой (в C++ — один `TEST` на кейс).

## 4.4 Субтесты и параллельность

`t.Run(name, fn)` даёт иерархию: `TestSign/positive` — видно, какая строка упала; фильтр `go test -run TestSign/positive` запускает один кейс. `t.Parallel()` — субтесты идут параллельно (тесты всегда гоняем с `-race` — лекция 3). До Go 1.22 в цикле требовалось `tt := tt` — узнавайте в чужом коде.

## 4.5 Helper, Cleanup, Skip, TestMain

- `t.Helper()` — в функциях-помощниках: стек при падении укажет на строку теста, а не на `setup`.
- `t.Cleanup(fn)` — «defer на уровень теста». Паттерн: `func setup(t *testing.T) *Store { ...; t.Cleanup(store.Close); return store }`.
- `t.Skip` — «неприменим здесь»; `testing.Short()` + `go test -short` — тяжёлые/интеграционные пропускаются.
- `TestMain(m *testing.M)` — один на пакет: тяжёлый общий setup (контейнер), `m.Run()`, teardown.
- Фикстуры: `t.TempDir()` (самоудаление), `t.Setenv`; golden files — эталонные файлы-ожидания рядом с тестом.

## 4.6 testify: assert vs require

`assert.Equal(t, want, got)` = `t.Errorf` (продолжить), `require.NoError(t, err)` = `t.Fatalf` (выйти немедленно) — выбор тот же, в одной строке. Порядок аргументов всегда `(t, expected, actual)`. Gotcha: `time.Time` сравнивать через `assert.True(t, want.Equal(got))` — `DeepEqual` учитывает монотонные часы и локацию. `testify/suite` — не идиоматичен (ломает table-driven и параллельность).

## 4.7 Моки: фейки, mockgen, prepare-паттерн

В Go мок — это **своя реализация интерфейса** (интерфейс объявляет потребитель — лекция 2), несколько строк рядом с тестом:

```go
type fakeStore struct{ users map[string]User }

func (f *fakeStore) Get(name string) (User, bool) {
	u, ok := f.users[name]
	return u, ok
}
```

Никакого Mockito с цепочками `when/thenReturn` — зоология fake/stub/spy почти не нужна. Для больших интерфейсов — **генерация**: `go.uber.org/mock/mockgen` (режимы package/source, `//go:generate`), рантайм с `EXPECT()` и автоматической проверкой ожиданий.

`prepare`-паттерн для табличных тестов: контроллер gomock создаётся внутри `t.Run` (свой на кейс), в строке таблицы — поле `prepare func(f *fields)`, навешивающее ожидания кейса. Граница: gomock — для проверки **взаимодействий**; простая подстановка значений — ручной фейк короче.

## 4.8 Фаззинг

Таблица проверяет кейсы; фаззинг проверяет **свойства** на тысячах сгенерированных входов:

```go
func FuzzReverse(f *testing.F) {
	f.Add("привет")                      // seed-корпус
	f.Fuzz(func(t *testing.T, s string) { // свойство
		r := []rune(s)
		rev := Reverse(r)
		rev2 := Reverse(rev)
		if !slices.Equal(r, rev2) {
			t.Fatalf("double reverse: %q != %q", s, string(r))
		}
	})
}
```

`go test` гоняет только сиды; `go test -fuzz=FuzzReverse -fuzztime=30s` — мутационный поиск с обратной связью по покрытию. Находка (паника/провал свойства) сохраняется в `testdata/fuzz/` и навсегда становится регресс-тестом. Живой случай с пары: фаззинг нашёл `"\xa9"` (битый UTF-8) — это не баг `Reverse`, а неточное свойство; уточнили контрактом. Цели — парсеры и всё, что ест внешний ввод.

## 4.9 Бенчмарки

```go
var sink int

func BenchmarkSum(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = sumTo(100)
	}
}
```

`go test -bench=. -benchmem`. `b.N` подбирается платформой. **Sink обязателен** — без него компилятор выкинет «бесполезный» вызов, и будем мерить пустоту (классическая ошибка первого бенчмарка). Вывод: `BenchmarkSum-8` (8 = GOMAXPROCS, сравнивать прогоны с разным нельзя), `ns/op`, и — с `-benchmem` — `B/op` и `allocs/op`: **аллокации часто важнее наносекунд** (каждая — давление на GC). `b.RunParallel` — под конкурентную нагрузку; общий счётчик — только атомарный. Прогон-с-прогоном «в лоб» не сравнивают — шум; нужен benchstat.

## 4.10 Покрытие

`go test -cover` — процент; `-coverprofile=c.out` + `go tool cover -html=c.out` — красные строки = кандидаты на новые кейсы. Честно: покрытие говорит, какие строки **исполнялись**, а не проверялись ли их результаты; 100% ≠ отсутствие багов, но низкое — плохой знак.

## 4.11 Тулинг

- **gofmt/goimports** — формат не настраивается; goimports правит импорты; спорить о стиле запрещено экосистемой.
- **go vet** — статический анализ из коробки (printf-форматы, копирование мьютекса, lostcancel); запускается автоматически внутри `go test`.
- **golangci-lint** — агрегатор (staticcheck, errcheck, revive, gosec...) с `.golangci.yml`; место — CI: «линтер ругается — MR не мержится» дешевле ревью.
- **Свой линтер** — за вечер на `go/analysis`: анализатор с `ast.Inspect`, находки через `pass.Reportf`, CLI через `singlechecker.Main`; тестирование — `analysistest` + `testdata` с `// want`-комментариями.
- **pprof** — `import _ "net/http/pprof"` + `go tool pprof`: профили CPU/heap/goroutine/block. Сегодня обзор; ловим реальные утечки на занятии 10.
- Бонус для любопытных: `goleak.VerifyNone(t)` — тест падает, если горутины не завершились (ловит утечки из занятия 3).

# Шпаргалка: что должно остаться в голове

Занятие 3:

1. `main` не ждёт горутины; правильное ожидание — WaitGroup, `Add` до запуска, `defer Done`.
2. Паника в горутине валит процесс; `recover` работает только в своей горутине.
3. Канал передаёт данные **и** синхронизацию; закрывает отправитель; отправка в закрытый — паника; nil-канал блокирует навсегда.
4. Гонка = два доступа без ребра happens-before; тесты всегда с `-race`.
5. Мьютекс — рядом с данными; канал — для владения, мьютекс — для состояния; RWMutex — для долгого чтения.
6. Каждая горутина-генератор должна уметь завершиться — `context` + `Done()`.
7. `ctx` — первый параметр; `defer cancel()` всегда; graceful shutdown = сигнал → ctx → Done → Wait.
8. `Once` — ровно раз; `Pool` — только кеш; `atomic` — одно значение; `errgroup` — первая ошибка + отмена; `singleflight` — дедупликация.

Занятие 4:

1. Тест — `TestXxx(t *testing.T)` в `*_test.go`; `go test ./...`.
2. Кейсы — строки таблицы; `t.Run` — читаемые отчёты и фильтр `-run`.
3. `Fatalf` — если дальше продолжать нельзя; `Errorf` — собрать всё.
4. `t.Helper`/`t.Cleanup`/`t.Skip`/`TestMain` — гигиена тестов.
5. Мок — реализация интерфейса; `mockgen` + `prepare` — для взаимодействий.
6. Бенчмарк вокруг `b.N` с sink; смотреть `allocs/op`.
7. Покрытие — карта непротестированных строк, не метрика качества.
8. `go vet` + `golangci-lint` — в CI; фаззинг — для свойств, находка живёт в `testdata/fuzz`.

# Конспект занятий 5–6: дженерики, стандартная библиотека и базы данных

# Занятие 5. Дженерики, JSON и стандартная библиотека

## 5.1 Зачем дженерики: цена `any`

Проблема: одна функция для многих типов. Без дженериков — либо копипаста (`MaxInt`, `MaxFloat`, `MaxString`), либо `any`. Цена `any` — три вещи:

1. **Boxing.** Значение интерфейса — пара «(дескриптор типа, данные)»; упаковка не-словесного значения — аллокация в кучу, давление на GC.
2. **Проверка типов — в рантайме.** `v.(int)` сравнивает дескрипторы при выполнении; промах — паника `interface conversion`.
3. **Компилятор молчит.** `MaxAny("go", 7)` компилируется; упадёт у пользователя в проде. `any` не даёт **ни одной** операции — даже `<`.

До-дженериковый обход — принимать функцию сравнения (так написан `sort.Slice`): работает, но типобезопасность держится на дисциплине.

**История.** Дилемма дженериков (Rob Pike): из трёх скоростей — программиста, компилятора, программы — выбери два. C++ выбрал программиста и программу (мономорфизация, тяжёлый компилятор), Java — программиста и компилятор (erasure + boxing), Go 1.0 — компилятора и программу (копипаста). Десять лет stdlib жила интерфейсами и `interface{}` + reflect. Черновик 2018 года (Taylor, Griesemer) с «contracts» отвергли как «язык в языке»; в редизайне 2020 contracts стали обычными интерфейсами с type sets. Proposal #43685 принят в 2021-м, релиз — Go 1.18 (2022). Итоговый дизайн **скромнее шаблонов**: нет специализации, метапрограммирования, перегрузки операторов; тело проверяется один раз при объявлении — ошибки компиляции читаемые.

## 5.2 Type parameters и почему скобки квадратные

```go
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

Max(3, 7)    // T = int — выведен сам
Max[int](3, 7) // тип можно указать явно
```

Главное отличие от C++-шаблонов: тело проверяется **при компиляции объявления** против constraint, а не при инстанциации — ошибку в теле видит автор, а не пользователь на другом типе.

Почему скобки именно `[]` (вопрос с design doc):

- **`<T>` не подошло**: конфликт с операторами сравнения. `a < b, c > d` — два сравнения или дженерик? C++ разруливает контекстным разбором и костылями вроде `typename`; грамматика Go принципиально однозначна, а `<`/`>` уже заняты.
- **`(type T)` — черновик 2018**: `func Print(type T)(s []T)`, инстанциация `Vector(int)`. Вызовы нечитаемы: `Print(int, nums)` неотличим от обычного вызова с двумя аргументами.
- **`[T]` победил**: не конфликтует ни с одним оператором; перекликается с индексацией (`Stack[T]` — «индексация по типу», как `m[key]` по ключу); скобки в Go уже параметризуют типы (`[N]T`, `map[K]V`).

## 5.3 Constraints: какие операции разрешены

Constraint — это **интерфейс**, знакомая механика, только про типы-параметры: он перечисляет, какие типы разрешены и какие операции над ними гарантированы.

```go
type Number interface {
	~int | ~int64 | ~float64 // union через |
}

func Sum[T Number](xs []T) T { ... }
```

- Union `|` — перечисление разрешённых типов; тело проверяется против **всего набора сразу**: сложение обязан поддерживать каждый.
- **`~`** — «любой тип с тем же underlying»: `type Celsius float64` не подошёл бы без тильды (присваивание несовместимо), с `~float64` — подходит.
- **Встроенные**: `comparable` — разрешает `a == b`; `cmp.Ordered` — разрешает `<` (числа и строки); `any` — разрешает всё, не даёт ни одной операции. Все они — обычные интерфейсы, можно посмотреть исходники.
- Комбинируются: встраивание (`cmp.Ordered` внутри своего), методы (`interface{ String() string }` — тоже constraint).
- **Правило минимальности**: constraint описывает ровно операции, которые использует функция. Шире `any` — в теле нельзя ничего; уже `Number` — `Max` на строках не написать.

Шпаргалка: сравнение `a == b` → `comparable`; порядок `a < b` → `cmp.Ordered`; сложение → свой union; ничего → `any`.

**Ограничение языка**: метод не может вводить собственные параметры типа — только использовать параметры своего типа. Обход — свободные функции: `Map[T, U any](s []T, f func(T) U)`.

## 5.4 Сортировка: было и стало

Лучший живой пример, зачем дженерики принимали.

**Было** — `sort.Interface`: под каждый ключ свой тип-обёртка с тремя методами:

```go
type ByAge []User

func (u ByAge) Len() int           { return len(u) }
func (u ByAge) Less(i, j int) bool { return u[i].Age < u[j].Age }
func (u ByAge) Swap(i, j int)      { u[i], u[j] = u[j], u[i] }

sort.Sort(ByAge(users))
```

Плюс `sort.Slice` — без обёртки, но `func(i, j int) bool` над `any`: типы не проверяются. В C++ `std::sort` с лямбдой был типизирован всегда — boilerplate `Len/Less/Swap` был одним из аргументов proposal #43685.

**Стало**:

```go
slices.SortFunc(users, func(a, b User) int {
	return cmp.Compare(a.Age, b.Age)
})
slices.Sort(xs) // для Ordered компаратор не нужен вовсе
```

Одна функция на любой тип и ключ; компилятор проверяет типы и сигнатуру (компаратор возвращает `int`: -1/0/+1, как `memcmp`, а не bool). Правило: в новом коде — `slices.Sort`/`SortFunc`/`SortStableFunc`/`IsSorted`; пакет `sort` — легаси.

## 5.5 cmp, slices, maps

`cmp.Compare`/`cmp.Less` — стандартная запись сравнения (NaN-безопасная). Пакеты `slices` (`Sort`, `Contains`, `Max`, `Index`, `Clone`, `Equal`) и `maps` (`Keys`, `Values`, `Clone`, `Copy`) существуют **потому, что появились дженерики** — до 1.21 это был `golang.org/x/exp`. Мапа не гарантирует порядок обхода — идиома детерминированного вывода: `slices.Sorted(maps.Keys(m))`. Правило: прежде чем писать утилиту — загляните в `slices`, она уже есть.

## 5.6 encoding/json: теги и приватные поля

JSON — формат по умолчанию для HTTP API, конфигов, JSONL-логов. В C++ это сторонние библиотеки (nlohmann/json, rapidjson); в Go — stdlib. И дидактически это **памятник до-дженериковой эпохи**: `json.Marshal(v any)` разбирает структуры через reflect в рантайме — теги читает рантайм, ошибки типов ловит рантайм (`*json.UnmarshalTypeError`). Контраст с дженериками намеренный: компиляция против выполнения.

**Теги** — аннотации над полями, читаются reflect'ом:

```go
type User struct {
	ID    int    `json:"id"`
	Email string `json:"email,omitempty"` // пустое — не писать
	Pass  string `json:"-"`               // в JSON не попадает
}
```

Без тега имя поля как объявлено (`Email`) — ломает lowercase-конвенцию JSON, поэтому теги ставят почти всегда.

**Приватные поля не сериализуются** и `Unmarshal` их тоже не заполнит: reflect видит только экспортированные поля. Это не недоработка, а правила видимости: чужой пакет не может читать приватные поля. Это фича — служебные поля делайте приватными, они гарантированно не утекут в API. Поле «пропало из json» — первым делом проверьте регистр первой буквы.

## 5.7 Анмаршализация и omitempty

```go
var u User
err := json.Unmarshal(data, &u)
```

- Только указатель: куда складывать результат.
- **Незнакомые поля JSON молча игнорируются** — с одной стороны совместимость, с другой: опечатка в имени поля не найдётся никогда. После `Unmarshal` — валидация.
- Чего не хватило — нулевое значение, **не ошибка**. Ошибка в одном поле — `*json.UnmarshalTypeError`, остальное распарсится.
- **`omitempty` скрывает нулевые значения, а не «пустые»**: `false`, `0`, `""`, `nil` пропадают. `Paid bool` с `omitempty` исчезнет при `false` — получатель не отличит «нет поля» от «ложь». Различать «не задано» — указатели (`*bool`) или типы с `.Valid`.

## 5.8 Кастомные маршаллеры, поток: Encoder/Decoder

`MarshalJSON`/`UnmarshalJSON` — те же интерфейсы из лекции 2: тип сам решает, как выглядеть в JSON. Кейсы — время в другом формате, decimal (деньги!), enum-строки, legacy. В `UnmarshalJSON` ошибки оборачиваем через `%w`.

`json.Marshal` требует весь объект в памяти; **Encoder/Decoder** работают с `io.Reader`/`io.Writer`:

```go
dec := json.NewDecoder(r)
for {
	var t Task
	if err := dec.Decode(&t); err != nil {
		break // io.EOF — данные кончились
	}
	// ...
}
```

JSONL (объект на строку) — стандарт для логов и стримов; `Encode` добавляет `\n` после объекта — не баг, а совместимость с JSONL. Было/стало в потребителях: раньше типобезопасную обёртку писали руками на каждый тип (`DecodeUser`...), теперь одна — `func Decode[T any](data []byte) (T, error)`. Честная оговорка: сам json не ускорился — reflect внутри остался.

## 5.9 io.Reader и io.Writer

Два однопроцедурных интерфейса держат весь ввод-вывод языка (в C++ — десятки stream-классов):

```go
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
```

Где встречаются: файлы (`*os.File`, `Stdin/Stdout/Stderr`), сеть (`net.Conn` — TCP-сокет одновременно Reader и Writer), HTTP (`Request.Body`, `ResponseWriter`), в памяти (`bytes.Buffer`, `strings.Reader`), сжатие (`gzip.Writer`), архивы (`tar`, `zip`), шифрование, `bufio`. Всё **комбинируется**: источник → трансформер → приёмник:

```go
f, _ := os.Create("log.gz") // приёмник: файл
gz := gzip.NewWriter(f)     // трансформер поверх любого Writer
gz.Write(data)              // сжали и записали, не зная деталей
gz.Close()
```

Следствие для дизайна: функция принимает `io.Reader`, а не `*os.File` — и её можно кормить чем угодно, тесты не требуют файловой системы: `ParseConfig(strings.NewReader("port=8080"))`.

**io.Copy и os**: `io.Copy(dst, src)` — вся «копилка буферов» внутри; писать цикл с `make([]byte, 4096)` — легаси. `os.ReadFile`/`os.WriteFile` — мелкие файлы целиком; `os.Open`/`os.Create` — потоково с `defer Close()`.

**bufio**: каждый `Read` — потенциально syscall; `bufio.Scanner` — построчное чтение, дефолт для текста. Две ловушки: лимит строки **64 КБ** (длинная строка → `token too long`, лечится `sc.Buffer`), и `Scan()` возвращает `false` и при конце данных, и при ошибке — проверять **`sc.Err()` после цикла**. `bufio.Writer` — та же экономия на записи; не забыть `Flush()`.

## 5.10 time и regexp

**time**: формат задаётся не шаблоном, а **эталонной датой** `2006-01-02 15:04:05 MST` — мнемоника `1 2 3 4 5 6 7`: месяц, день, час, минута, секунда, год, зона. Сначала бесит, через неделю вспоминается без документации. `time.RFC3339` — готовая константа, и это тот же формат, в который json пишет `time.Time`. `time.Duration` — просто int64 наносекунд; `time.Since`, `t.Sub` — для измерений (бенчмарки).

**regexp**: синтаксис RE2 — гарантированное **линейное** время; катастрофического бэктрекинга, на котором вешают `std::regex`, не существует. Цена: нет backreferences и lookahead (в 90% случаев хватает групп и `$1` в `ReplaceAllString`). `regexp.MustCompile` на уровне пакета — компиляция один раз; упать на деплое лучше, чем в проде на первой строке.

# Занятие 6. Работа с базами данных

## 6.1 database/sql — это НЕ драйвер

Два слоя: **`database/sql`** — словарь приложения (`*sql.DB`, `*sql.Rows`, `*sql.Tx`, `*sql.Stmt`), **`database/sql/driver`** — контракт для авторов драйверов. Драйвер регистрируется в своём `init()` через `sql.Register`; blank-импорт — единственное место, где приложение знает про драйвер (плюс DSN):

```go
import (
	"database/sql"
	_ "github.com/jackc/pgx/v5/stdlib"
)
db, err := sql.Open("pgx", dsn)
```

Аналогия для C/C++: ODBC-слой, встроенный в stdlib (Java — JDBC). Смена СУБД — смена драйвера и диалекта, не переписывание кода (в пределах базовых операций). Цена абстракции — общий знаменатель: jsonb/массивы/uuid через `database/sql` неудобны.

## 6.2 Драйверы Postgres

- `lib/pq` — исторический, maintenance-режим; текстовый протокол. В старом коде — узнавать, не тащить.
- `pgx/v5` — стандарт де-факто, бинарный протокол (быстрее, меньше аллокаций). Два режима: **через stdlib** (остаёмся в `database/sql`, совместимы sqlx/sqlc) и **нативный** (`pgxpool`) — максимум Postgres.
- Что даёт нативный режим: **`pgtype`** (uuid, jsonb, массивы — прямо в `Scan`, без ручных конвертаций), **`COPY`** (потоковая массовая вставка: миллион строк — секунды вместо минут), **batch** (несколько команд в один сетевой round-trip), **`LISTEN/NOTIFY`** (шина сообщений PG — инвалидация кэшей; подписка сессионная, живёт на конкретном соединении).
- Многохостовые кластеры — `golang.yandex/hasql`: выбор живого хоста и роли (writer/reader).
- Выбор по умолчанию — pgx через stdlib; нативный — осознанная сделка «привязка к Postgres в обмен на возможности».

## 6.3 Подключение: Open ленив, пул, а когда пул не нужен

- `sql.Open` **не открывает соединение** — только парсит DSN. Реальная проверка — `PingContext(ctx)` (демо: битый DSN — Open молчит, Ping падает). На старте сервиса — пинг с ретраями.
- `*sql.DB` — **пул соединений**, горутинобезопасен: одна на приложение, а не на запрос.
- **Когда пул не нужен** (CLI-утилита, скрипт): `conn, err := db.Conn(ctx)` — закреплённое соединение, сессия живёт до `conn.Close()` (это возврат в пул, не закрытие). Сессия нужна для temp tables, advisory locks, `LISTEN/NOTIFY` — они живут на конкретном коннекте. Ещё проще — `db.SetMaxOpenConns(1)`. В нативном pgx: `pgx.Connect` — один коннект, `pgxpool` — по желанию.

## 6.4 Чтение: QueryRow и Query

```go
var name string
err := db.QueryRowContext(ctx,
	`SELECT name FROM users WHERE id = $1`, id).Scan(&name)
if errors.Is(err, sql.ErrNoRows) {
	return fmt.Errorf("user %d: %w", id, ErrNotFound)
}
```

- `sql.ErrNoRows` — не ошибка, а ответ: «строки нет» — это 404, а не 500. Sentinel различаем `errors.Is`, оборачиваем `%w` (лекция 2).
- `rows` (от `QueryContext`) — **курсор, держащий соединение из пула**. Не закрыл — соединение утекло; под нагрузкой пул иссякнет за секунды. `defer rows.Close()` — рефлекс.
- **`rows.Err()` после цикла** — обязателен: `Next()` возвращает false и на конце данных, и на обрыве сети; без него половина списка неотличима от целого.
- В цикле — только `Scan` («собери и работай»); вложенный Query в цикле при маленьком `MaxOpenConns` — **дедлок на пуле**: горутина держит соединение №1 и ждёт №2. `-race` это не ловит — не гонка, а логическая блокировка.
- `Scan` привязан к колонкам по позиции: `SELECT *` рядом с чужим `ALTER TABLE` — ошибка в рантайме.

## 6.5 Запись: Exec, RowsAffected, RETURNING

- `ExecContext` — для INSERT/UPDATE/DELETE. `RowsAffected` — сколько реально изменено; оптимистичные проверки: `UPDATE ... WHERE id = $2 AND status = 'new'` вернул 0 — статус уже сменили (гонка поймана без транзакции).
- `LastInsertId` — MySQL-наследие интерфейса, в Postgres **не работает**. Одна поездка вместо двух: `INSERT ... RETURNING id` — и RETURNING может вернуть любые колонки и выражения.

## 6.6 Параметры — только плейсхолдеры

`$1, $2` (в MySQL `?`) — значение едет отдельно от текста запроса; драйвер сам экранирует и типизирует. Конкатенация пользовательской строки — SQL-инъекция, уязвимость №1 веба: `"x'; DROP TABLE users; --"`. Нюанс: параметризуются только **значения** — имена таблиц/колонок и направление ORDER BY — часть структуры запроса; приходят извне — только через белые списки.

## 6.7 Транзакции и уровни изоляции

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
	return err
}
defer tx.Rollback() // после Commit — no-op

if _, err := tx.ExecContext(ctx, `UPDATE ...`, ...); err != nil {
	return err
}
return tx.Commit()
```

- Внутри транзакции — **только методы `tx`**, НЕ `db`: запрос через `db` уедет по другому соединению и вне атомарности.
- `defer tx.Rollback()` — страховка: при забытой ошибке транзакция не повиснет с локами.
- Транзакция — короткая: никаких внешних API внутри.
- Изоляция: Read Committed (дефолт PG) — каждый запрос видит свежий снимок; Repeatable Read — снимок на транзакцию; Serializable — «как последовательно», конфликты = **ошибка сериализации, которую ретраят** (норма, не баг). Проблемы те же, что в памяти (лекция 3), механизмы другие — MVCC и блокировки.

## 6.8 context: почему у методов две версии

Хронология, объясняющая странность пакета: **2011–2012** — `database/sql` появился в Go 1.0, когда контекста ещё не существовало; **2014** — `golang.org/x/net/context`, обкатка вне stdlib; **2016, Go 1.7** — контекст в stdlib и `net/http`; **2017, Go 1.8** — в `database/sql` завезли параллельный набор `*Context`-методов.

Почему параллельный, а не «добавить параметр»: в Go нет перегрузки функций, а менять сигнатуру старых нельзя из-за обещания совместимости Go 1. Поэтому старые методы остались навсегда — как тонкие обёртки:

```go
func (db *DB) Query(query string, args ...any) (*Rows, error) {
	return db.QueryContext(context.Background(), query, args...)
}
```

`context.Background()` — «вечный» контекст: старые методы — это контекстные с выкрученной в ноль отменой. Отмена едет **до драйвера**: драйвер держит горутину на `ctx.Done()`, ставит дедлайн на сокет и снимает запрос на стороне PG (аналог `pg_cancel_backend`); вместо зависания — `DeadlineExceeded`, соединение возвращается в пул. Правило: в новом коде — только `*Context`-методы; гигиена — `Background` только наверху, `nil`-контекст паникует, контекст не хранят в структурах.

## 6.9 Пул соединений: настройки и дедлок

- Установка соединения — TCP-handshake + аутентификация: миллисекунды на запрос недопустимы, пул переиспользует.
- `SetMaxOpenConns` — потолок (иначе лавина соединений и `max_connections` сервера); `SetMaxIdleConns` — тёплый запас; **`SetConnMaxLifetime`** — обязательно в проде: соединения протухают (рестарт БД, фейловер балансировщика).
- Настраивают оба конца: сумма лимитов инстансов приложения должна влезать в `max_connections`. Мерить — `db.Stats()`.

## 6.10 NULL

`NULL` ≠ нулевое значение: `Scan` в `string` при NULL — ошибка `converting NULL to string is unsupported`. Три способа: `sql.Null*` (`.Valid` + значение), указатели (`*string`, NULL → `nil`), `COALESCE` в SQL. В API-моделях чаще указатели; в pgx — `pgtype` (массивы, jsonb, uuid).

## 6.11 Надстройки и ORM: сравнение

| Инструмент | Суть | Плюсы | Минусы |
| --- | --- | --- | --- |
| sqlx | надстройка над `database/sql` | `Scan` в структуры, минимум магии | SQL пишется руками, reflect |
| sqlc | генератор кода из SQL | типобезопасность, SQL виден явно | динамические запросы неудобны |
| pgx нативный | драйвер Postgres | скорость, типы и фичи PG | привязка к Postgres |
| gorm | ORM | быстрый старт, большая экосистема | N+1, неявный `SELECT *`, магия |
| ent | ORM + кодогенерация | типобезопасный граф связей | высокий порог входа |

- **sqlx** — тот же `*sql.DB` под капотом: `SelectContext`/`GetContext` сканируют в структуры по тегам `db:"..."`; плюс именованные аргументы `:name` через `NamedExec` (работают на любом драйвере, тоже против инъекций).
- **sqlc** — генератор: SQL с аннотациями → типобезопасные функции (`sqlc generate`). Ошибки в SQL — при генерации, типы — компилятором. Минус — динамические запросы: собрать WHERE «если флаг включён» нельзя; либо запрос на каждую комбинацию фильтров, либо фиксированный запрос с выключаемыми условиями (`sqlc.arg('name') = '' OR name = sqlc.arg('name')`) — читается тяжело, и планировщик PG держит один универсальный план. Идеален для фиксированного набора запросов; для «конструкторов» — руки (`QueryContext` + `Scan`).
- **По умолчанию** — pgx + sqlc; gorm — CRUD-прототип; ent — сложные связи. Общее предпочтение сообщества — явный SQL.
- **Не-SQL**: Redis — `go-redis/redis` (свой протокол RESP, не database/sql, но те же идеи: клиент + ctx + пул); ClickHouse — драйвер совместим с `database/sql` (`sql.Open("clickhouse", dsn)`); MongoDB — `mongo-go-driver`. `database/sql` — только для SQL.

## 6.12 Тестирование репозитория и миграции

- Репозиторий за **интерфейсом** (`UserRepository`), который объявляет сервис (лекция 2): сервис тестируется с фейком без БД, SQL живёт в одном месте.
- **sqlmock** подменяет драйвер: `ExpectQuery`/`WithArgs`/`WillReturnRows` — сценарий; проверяются и SQL, и параметры; `ExpectationsWereMet` — все ли ожидания выполнены. Ограничение: sqlmock проверяет, что шлём задуманный SQL, но не что он корректен для схемы.
- **testcontainers-go** — реальный Postgres в Docker на время теста: честное поведение. В зрелых проектах — оба уровня. `-race` обязателен.
- **Миграции** — схема версионируется как код: нумерованные файлы (`0001_...sql`) с up/down, в БД — таблица с текущей версией, инструмент накатывает недостающее. **goose** — обычный SQL с комментариями `-- +goose Up` / `-- +goose Down`, CLI (`goose up`) и из кода (`goose.Up(db, "migrations")`). Применённую миграцию не редактируют. Альтернативы: `golang-migrate` (мощный CLI), **atlas** (декларативный: сам считает дифф и линтует опасные изменения). На деплое — expand/contract: старый бинарь живёт, пока новый накатил схему.

# Шпаргалка: что должно остаться в голове

Занятие 5:

1. Дженерик — параметр типа с constraint (проверка при объявлении); интерфейс — контракт поведения (проверка в рантайме).
2. `~` — по underlying; `comparable` для `a == b`, `cmp.Ordered` для `<`; методы не параметризуют — свободные функции.
3. Сортировка: `slices.Sort`/`SortFunc` + `cmp.Compare`; `sort.Interface` — легаси.
4. Прежде чем писать утилиту — `slices`/`maps`/`cmp` уже есть.
5. JSON: теги всегда; приватные поля не сериализуются; `omitempty` скрывает нулевые значения; после `Unmarshal` — валидация; поток — Encoder/Decoder.
6. Функции принимают `io.Reader`/`io.Writer`; `strings.NewReader` — тесты без файловой системы.
7. Scanner: лимит 64 КБ и `Err()` после цикла.
8. Layout time — эталонная дата; json пишет time.Time в RFC3339; regexp RE2 — линейно, без lookahead.

Занятие 6:

1. `*sql.DB` — пул, одна на приложение; `Open` ленив, проверка — `PingContext`.
2. `rows` держит соединение: `defer rows.Close()` + `rows.Err()`; вложенный запрос в цикле — дедлок пула.
3. Плейсхолдеры только для значений; конкатенация — инъекция.
4. В транзакции — только `tx`; `defer tx.Rollback()`; Serializable — с ретраями.
5. Только `*Context`-методы: старые — обёртки над `context.Background()`.
6. `NULL` ≠ нулевое значение: `Null*`-типы или указатели.
7. Выбор: pgx+sqlc — контроль; gorm — прототип; ent — сложные связи.
8. `database/sql` — только для SQL: Redis/Mongo — свои клиенты.
9. Схема — миграциями (goose); применённую не редактируют; деплой — expand/contract.
